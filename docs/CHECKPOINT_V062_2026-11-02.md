## Defeito reproduzido ANTES

O código atribuía `draft-${Date.now().toString(36)}` aos novos rascunhos e `sched-${Date.now().toString(36)}` às programações. Dois registros feitos no mesmo milissegundo recebiam **o mesmo ID**. Essa colisão tornava ambíguas as ações por `data-draft`/`data-schedule` e os vínculos `proposalId`, mesmo que ambos os itens estivessem visíveis. Um teste com relógio congelado falhou no primeiro viewport de 280 px, exibindo dois rascunhos diferentes com ID `draft-mitvfg1s`.

## Correção mínima

- `src/main.ts`: acrescentada `nextLocalRecordId(prefix, records)`, que conserva o antigo padrão timestamp enquanto ele é único e acrescenta um sufixo crescente **apenas quando já existe o ID no conjunto local**, incluindo programações canceladas. Os IDs antigos permanecem intactos e a restauração/quarentena preexistentes continuam as fontes de verdade. Nenhuma dependência nova, alteração de dados, layout ou API.
- `tests/browser_workflow_id_collision_v0152.py`: teste regressivo em Chromium offline com `Date.now()` fixo em quatro larguras (280, 390, 740, 1280 CSS px). Cria dois rascunhos, conclui uma terceira proposta, cria duas programações no mesmo instante, cancela apenas a segunda e confirma a integridade dos links e dos registros armazenados. Não utiliza autenticação ou dados reais.

## Limites e próximo passo

Esta é uma correção de **identificadores de registros de sessão fictícios**, não um identificador institucional global, sistema de histórico auditável no servidor, garantia criptográfica ou integridade transacional compartilhada. Não justifica marcar como concluídos os vínculos de contas reais, a colaboração Socii, autorização ou votação. Futuras implementações autenticadas precisarão de IDs e transações do backend.
